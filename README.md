Reproducibility Instructions for Reviewers

This repository contains the prototype source code, Kubernetes manifests, model training/export scripts, experiment automation scripts, numerical CSV summaries, and raw measurement files used in the manuscript.

Requirements

The experiments were prepared and tested in the following environment:

Java 21
Maven
Python 3.10+
Docker Desktop with Kubernetes enabled, or another local Kubernetes cluster
kubectl
1. Clone the repository
git clone https://github.com/TimoBond/onnx-spring-boot-orchestrator.git
cd onnx-spring-boot-orchestrator
2. Build and test the Spring Boot ONNX component
cd ai-client
./mvnw test

On Windows:

cd ai-client
mvnw.cmd test

This verifies the Java/Spring Boot part of the prototype, including ONNX Runtime integration and the rule-based decision logic.

3. Prepare the Python environment

From the repository root:

cd target-app
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

On Windows:

cd target-app
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
4. Run the Kubernetes prototype

Apply the Kubernetes manifests:

kubectl apply -f ai-client/k8s/rbac.yaml
kubectl apply -f ai-client/k8s/target-workload.yaml
kubectl apply -f target-app/target-app-deploy.yaml
kubectl apply -f target-app/nodeport.yaml

Check the deployment status:

kubectl get pods
kubectl get svc
5. Reproduce the experimental workflow

The load-generation and monitoring scripts in target-app/ can be used to reproduce the prototype-level experiments:

python load_gen.py
python monitor_loop.py

The CSV files included in the repository contain the numerical outputs used for the manuscript tables and figures. They can be inspected directly or regenerated by rerunning the corresponding scripts in the same environment.

Note

Small numerical differences are expected because latency measurements depend on the local machine, Docker/Kubernetes configuration, background system load, and JVM/Python warm-up state. The main reproducibility target is the experimental workflow and the relative comparison between the REST/Python sidecar path and the embedded ONNX/JVM path.
